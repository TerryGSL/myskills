# Investigate — 系统调试方法论

## 铁律

**不查根因，不做修复。**

看到症状就改代码 = 贴创可贴。必须先搞清楚**为什么**坏了，再动手修。

---

## Phase 1: 根因调查

1. **收集症状**：错误信息、日志、复现步骤、影响范围
2. **读相关代码**：不猜，看源码
3. **检查最近变更**：`git log --oneline -20`、`git diff HEAD~5` — 最近改了什么？
4. **复现**：在本地跑一遍，确认能复现。不能复现的 bug 先搞清楚复现条件。
5. **范围锁定**：确定受影响的模块后，后续编辑**锁定在该模块内**，防止改着改着跑偏。

---

## Phase 2: 模式分析

把症状匹配到已知模式：

| 模式 | 典型症状 | 排查方向 |
|------|---------|---------|
| 竞态条件 | 偶发、并发时出现、重试就好 | 锁机制、原子操作、事务隔离 |
| 空指针传播 | `undefined is not a function` / `NullPointerException` | 上游数据源、可选链、默认值 |
| 状态腐化 | 明明初始化了但状态不对 | 状态机流转、并发写入、缓存一致性 |
| 集成故障 | 本地没问题，联调就挂 | 协议不匹配、序列化、超时设置 |
| 配置偏移 | 部署后才出现 | 环境变量、配置文件差异、feature flag |
| 缓存过期 | 改了数据但显示旧值 | 缓存失效策略、TTL、缓存键 |

不匹配任何已知模式 → 跳到 Phase 3 从头形成假设。

---

## Phase 3: 假设验证

**流程**：
1. 形成假设：「我认为问题出在 X，因为 Y」
2. 设计验证：加调试输出 / 打断点 / 写临时测试
3. 运行验证
4. 结果判断：
   - 假设正确 → Phase 4
   - 假设错误 → 搜索相关错误信息，形成下一个假设

**3-Strike 规则**：
- 第 1 个假设错了：正常，继续
- 第 2 个假设错了：仔细想想是不是方向就错了
- 第 3 个假设错了：**停止**。不要再猜了。
  ```
  ⚠️ 需要决策

  状态：阻塞
  问题：3 次假设验证均失败，根因尚未确定
  已尝试：
    1. [假设 1 及验证结果]
    2. [假设 2 及验证结果]
    3. [假设 3 及验证结果]
  建议：[可能需要更多上下文 / 换个角度 / 找相关经验的人看看]
  ```

---

## Phase 4: 实现修复

确认根因后：

1. **修根因**，不修症状。如果根因在 A 但症状在 B，修 A 不修 B。
2. **最小 diff**。只改必须改的，不顺手重构。
3. **爆炸半径检查**：如果修复涉及 > 5 个文件 → 先确认用户同意再动手。
4. **回归测试**：写一个测试，修复前失败、修复后通过。
5. **全量测试**：跑项目的完整测试套件，确认没有引入新问题。
6. **重新复现**：用原始复现步骤验证 bug 确实修好了。
