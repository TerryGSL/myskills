## 1. 设计背景与动机

### 1.1 问题：AI 编程的「失控」困局

当我们让 AI 直接写代码时，常常遇到这样的问题：

```
用户说："帮我加一个用户认证功能"

然后 AI 就开始……

❌ 不做需求分析，直接上手写代码
❌ 不考虑架构，随便往哪个文件塞逻辑
❌ 写完不测试，声称 "应该可以了"
❌ 没有安全审查，明文存密码也不管
❌ 写了 500 行代码，最后一个 typo 导致全部白费
```

**核心矛盾**：AI 有足够的编码能力，但缺乏工程纪律。

### 1.2 解法：把软件工程流程变成 AI 的「操作系统」

Harness-Workflow 的设计灵感来自真实的工程团队协作模式：

```
在一个成熟的工程团队里：

产品经理 ──→ 写需求文档
架构师   ──→ 审查设计、定契约
高级工程师 ──→ 写核心模块、Code Review
初级工程师 ──→ 写 CRUD 和业务逻辑
QA 工程师  ──→ 编写测试、验收
安全工程师 ──→ 安全审计

每个角色有明确的输入/输出，上游不合格则打回。
```

我们把这套协作模式编码成了 AI 的技能系统——每个角色是一个 Skill，每个阶段有明确的准入准出标准。

## 2. 核心设计理念

### 2.1 六大原则

```
┌─────────────────────────────────────────────────────────────────┐
│                     Harness-Workflow 设计原则                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ① 阶段门控  ──  每个阶段有明确的准入/准出标准，不合格不放行        │
│                                                                 │
│  ② 角色隔离  ──  不同 Agent 只能操作自己负责的文件和目录            │
│                                                                 │
│  ③ 契约冻结  ──  API 契约在实现阶段开始后冻结，防止「边写边改」      │
│                                                                 │
│  ④ 自动分级  ──  根据任务复杂度自动决定走哪些阶段，避免过度流程       │
│                                                                 │
│  ⑤ 状态持久  ──  所有进度写入文件，会话崩溃后可断点恢复              │
│                                                                 │
│  ⑥ 人在回路  ──  关键决策（push/部署）必须人工确认                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 设计哲学："不信任任何单一 Agent"

```
传统 AI 编程：

    用户 ──→ AI Agent ──→ 代码
              (单点)
              
Harness-Workflow：

    用户 ──→ 需求分析 ──→ 架构审查 ──→ 规划 ──→ 实现
                                                  │
              ┌───────────────────────────────────┘
              ▼
         Spec 审查 ──→ 质量审查 ──→ QA 测试 ──→ 安全审查 ──→ 交付
         
    每个环节都在审查上一个环节的产出，形成多层校验
```

## 4. 八阶段工作流详解

### 4.1 阶段总览

```
┌────────┬───────────────────┬──────────────┬───────────────────────────┐
│ Stage  │ 名称               │ 执行 Agent   │ 产出                       │
├────────┼───────────────────┼──────────────┼───────────────────────────┤
│   0    │ 需求分析            │ team-pd      │ PRD.md + DESIGN.md        │
│   1    │ 架构审查            │ team-architect│ ARCHITECTURE.md + 核心代码 │
│   2    │ 实现规划            │ writing-plans│ IMPL-PLAN.md              │
│   3    │ 编码实现            │ senior + junior│ 业务代码 + 单元测试      │
│   4    │ Spec 审查           │ 自动/Codex   │ 修复清单                  │
│   5    │ 质量审查            │ code-reviewer│ CODE-REVIEW.md            │
│   6    │ QA 测试             │ team-qa      │ TEST-REPORT.md            │
│   7    │ 安全审查            │ team-security│ SECURITY-REVIEW.md        │

└────────┴───────────────────┴──────────────┴───────────────────────────┘
```

### 4.2 Stage 0：需求分析（team-pd）

**目标**：把用户一句话的需求变成结构化的产品文档。

```
输入：用户需求（"加一个用户认证功能"）
       │
       ▼
┌─────────────────────────────────────────────────┐
│                 team-pd 产品设计师                │
│                                                  │
│  1. 解析需求 → 明确边界（做什么 / 不做什么）        │
│  2. 编写用户故事（谁 / 什么场景 / 什么价值）        │
│  3. 定义验收标准（Happy Path + 异常路径）          │
│  4. 评估数据需求（需要什么字段 / 关系）             │
│  5. 定义非功能需求（性能 / 安全 / 可用性）          │
│                                                  │
│  条件输出：                                       │
│  ├── UI 项目 → DESIGN.md (配色/字体/间距/组件)     │
│  └── API 项目 → API-SPEC.md (命名/版本/错误码)     │
└─────────────────────────────────────────────────┘
       │
       ▼
输出：docs/01-requirements/PRD.md
      docs/02-design/DESIGN.md 或 API-SPEC.md
```

**PRD 文档结构**：

```markdown
## PRD 模板结构

### 1. 背景与目标
   - 为什么做这个功能？解决什么问题？

### 2. 范围定义
   - IN SCOPE：本次要做的
   - OUT OF SCOPE：明确不做的

### 3. 用户故事（按优先级排序）
   - P0（必须）：核心功能
   - P1（应该）：重要但可延期
   - P2（可选）：锦上添花

### 4. 验收标准
   每个用户故事的 Happy Path + Error Cases

### 5. 数据需求
   需要哪些实体、字段、关系

### 6. 非功能需求
   性能目标、安全要求、可用性标准
```

### 4.3 Stage 1：架构审查（team-architect）

**目标**：审查设计是否有「黑洞」，输出架构契约。

```
输入：PRD.md + DESIGN.md
       │
       ▼
┌─────────────────────────────────────────────────┐
│             team-architect 架构师                 │
│            （Linus Torvalds 风格）                │
│                                                  │
│  Phase 1: 设计审判 ──────────────────────────    │
│  │                                               │
│  │  检查清单：                                    │
│  │  □ 幂等性 ── 重复请求会不会产生副作用？          │
│  │  □ 竞态条件 ── 并发操作会不会冲突？              │
│  │  □ 级联删除 ── 删父记录时子记录怎么办？          │
│  │  □ 权限漏洞 ── 水平越权 / 垂直越权？            │
│  │  □ 状态死胡同 ── 状态机有没有走不通的路？         │
│  │                                               │
│  │  任何一项不通过 → 打回 team-pd 重做             │
│  │                                               │
│  Phase 2: 输出架构文档 ─────────────────────     │
│  │                                               │
│  │  Section 1: 技术栈选择（含被拒方案的理由）       │
│  │  Section 2: 目录结构 + 权限矩阵                │
│  │  Section 3: 数据库 Schema (DDL + 索引)         │
│  │  Section 4: API 契约 (实现阶段后冻结 🔒)       │
│  │  Section 5: 核心基础设施代码                    │
│  │  Section 6: 安全架构                           │
│  │  Section 7: 架构决策记录 (ADR)                 │
│  │                                               │
│  Phase 3: 脚手架搭建 ──────────────────────     │
│  │                                               │
│  │  亲手编写核心代码：                             │
│  │  - 异常处理器                                  │
│  │  - 认证中间件                                  │
│  │  - 数据库连接池                                │
│  │  - CORS 配置                                  │
│  │  - 日志框架                                   │
│  │                                               │
└─────────────────────────────────────────────────┘
       │
       ▼
输出：docs/03-architecture/ARCHITECTURE.md
      src/core/ 目录下的基础设施代码
```

**关键设计：API 契约冻结机制**

```
                 Stage 0        Stage 1         Stage 2         Stage 3
                    │              │               │               │
API 契约状态：    不存在 ────→  定义并锁定 ───→  可引用 ────→  🔒 完全冻结
                                   │                               │
                                   │                               │
                              可以修改              不可以修改，只能实现
                              
为什么冻结？
──────────────
如果 API 契约在实现阶段还能改：
  → junior-dev 按旧契约写了一半
  → architect 改了 API 参数
  → junior-dev 的代码全废了
  → 陷入无限循环

冻结后的变更流程：
  → 必须新开一个 Round
  → 走完整的 Stage 0-1 重新评审
  → 旧 Round 的实现保持不变
```

```

│     │ • 30 分钟 - 2 小时   │ 实现一个搜索过滤器                   │
├─────┼────────────────────┼─────────────────────────────────────┤
│  L  │ • 10+ 个文件         │ 重构认证系统                        │

│  XL │ • 多个子系统          │ 从单体拆微服务                      │
│     │ • 需要拆分多轮执行     │ 全站国际化改造                      │
│     │ • 一天以上            │ 全新项目从零搭建                     │
└─────┴────────────────────┴─────────────────────────────────────┘
```

### 6.2 各级别的阶段裁剪

```
S 级任务（简单修复）:
──────────────────────────────────────────────────────────────
Stage:  0   1   2   3   4   5   6   7   8
        ⊘   ⊘   ✅   ✅   ✅   ✅   ⊘   ⊘   ✅
              跳过需求分析和架构       跳过 QA 和安全
              (太小没必要)            (改动太小风险低)

M 级任务（标准功能）:
──────────────────────────────────────────────────────────────
Stage:  0   1   2   3   4   5   6   7   8
        ✅   ⊘   ✅   ✅   ✅   ✅   ✅   ⊘   ✅
              跳过架构审查                 跳过安全审查
              (无架构变更)                (非敏感功能)

L 级任务（重大重构）:
──────────────────────────────────────────────────────────────
Stage:  0   1   2   3   4   5   6   7   8
        ✅   ✅   ✅   ✅   ✅   ✅   ✅   ✅   ✅
                    全部阶段都走

XL 级任务（系统级变更）:
──────────────────────────────────────────────────────────────
        自动拆解为多个 M/L 级 Round
        
        Round 1 (M): 基础设施搭建
        Round 2 (L): 核心模块实现
        Round 3 (M): 业务模块迁移
        Round 4 (M): 测试 + 文档
        
        每个 Round 独立走 Stage 0-8
```

**为什么要自动分级？**

```
没有分级的世界：

  用户: "改一个 typo"
  AI: "好的，让我先写 PRD..."
  AI: "现在做架构审查..."
  AI: "启动安全扫描..."
  用户: "...就改一个字而已 😤"

有了分级的世界：

  用户: "改一个 typo"
  AI: "S 级任务，跳过需求分析、架构、QA、安全"
  AI: "直接：规划 → 改代码 → 审查 → 完成"
  用户: "👍"
```

## 8. 并行调度与任务编排

### 8.1 task-dispatcher 工作原理

```

│                                                          │

│                                                          │

│          B ──────┤               │                        │

│                                                          │
```

### 8.2 并行安全规则

```
┌──────────────────────────────────────────────────────────┐
│               并行 Agent 的三条铁律                       │
│                                                          │
│  1. 零共享状态                                            │
│     ────────────                                         │
│     Agent A 和 Agent B 看不到彼此的存在                    │

│                                                          │
│  2. 文件不冲突                                            │
│     ──────────                                           │
│     两个 Agent 绝对不编辑同一个文件                        │
│     dispatcher 在分配时保证文件列表不重叠                   │
│                                                          │
│     ✅ Agent A: src/core/auth.ts                         │
│     ✅ Agent B: src/modules/user/service.ts              │
│     ❌ Agent A: src/shared/types.ts                      │
│     ❌ Agent B: src/shared/types.ts  ← 冲突!             │
│                                                          │
│  3. 结果合成                                              │
│     ────────                                             │
│     主 Agent 负责读取所有子 Agent 的结果                   │

│                                                          │

```

```

│                                                          │
```

```
│  │                                               │       │

│  └──────────────────────────────────────────────┘       │
│                                                          │
│  ┌──────────────────────────────────────────────┐       │

│  │                                               │       │

│  │     ── 否 → 可能卡住了                        │       │
│  │                                               │       │
│  │  2. 上次更新距今多久？                         │       │
│  │     ── < 10min → 正常                         │       │

│  │     ── > 30min → 大概率挂了，记录告警          │       │

│  │  3. 异常检测：                                 │       │

│                                                          │
│  ┌──────────────────────────────────────────────┐       │
│  │                Stage 8 收尾时                  │       │
│  │                                               │       │
│  │  CronDelete(cronJobId) → 停止心跳             │       │
│  │  .harness-status.json 保留 → 可查历史          │       │
│  └──────────────────────────────────────────────┘       │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

```
│   → 安装 i18n 库、配置 locale、抽取工具            │
│                                                  │
│ Round 2 (L): 核心模块国际化                       │
│   → 路由、认证、错误处理、API 响应                 │
│                                                  │
│ Round 3 (M): 业务模块国际化                       │
│   → 各业务页面/接口的文案抽取                      │
│                                                  │
│ Round 4 (M): 测试 + 文档 + 发布                   │
│   → E2E 多语言测试、翻译文件补全、文档更新          │
└─────────────────────────────────────────────────┘

执行流程：

Round 1 ──→ Stage 0~8 ──→ commit ──→ 自动开始
Round 2 ──→ Stage 0~8 ──→ commit ──→ 自动开始
Round 3 ──→ Stage 0~8 ──→ commit ──→ 自动开始
Round 4 ──→ Stage 0~8 ──→ commit ──→ 完成，询问 push
```

### 12.2 Round 间的依赖管理

```
┌──────────────────────────────────────────────────────────┐
│ Round 间的依赖管理                                        │
│                                                          │
│ Round N 完成后 → 进入 Round N+1 时：                      │
│                                                          │
│ 1. 读取 Round N 的 completedRounds 记录                  │
│    → 了解上一轮做了什么                                    │
│                                                          │
│ 2. 重新读取 .harness-context.json                        │
│    → 上一轮可能安装了新依赖，改变了技术栈配置               │
│                                                          │
│ 3. 重新评估当前 Round 的 scale                            │
│    → 上一轮的产出可能让当前轮变简单或复杂                   │
│                                                          │
│ 4. 如果上一轮有未修复的 P2/P3 Bug                         │
│    → 加入 knownIssues[]                                   │
│    → 当前轮可以选择修复或跳过                              │
│                                                          │
│ 原则：                                                    │
│ • 每个 Round 是自包含的（有自己的 Stage 0-8）              │
│ • 但继承上一轮的状态（代码 + 文档 + 已知问题）              │
│ • 不会重做上一轮已完成的工作                               │
└──────────────────────────────────────────────────────────┘
```

## 15. 关键设计决策回顾

### 15.1 为什么这样设计？

```
┌───────────────────────────────────────────────────────────────────┐
│                      关键设计决策及理由                             │
├──────────────────────┬────────────────────────────────────────────┤
│ 决策                  │ 理由                                      │
├──────────────────────┼────────────────────────────────────────────┤
│ 固定 8 个阶段，       │ 可预测、可测试、无意外。每个阶段有明确       │
│ 不做灵活流程          │ 的输入/输出。调试时可以精确定位哪个阶段       │
│                      │ 出了问题                                   │
├──────────────────────┼────────────────────────────────────────────┤
│ 自动分级而非           │ 避免小任务走完整流程（用户会崩溃），也避免     │
│ 用户手动选级          │ 大任务跳过关键阶段（质量会崩溃）。AI 根据      │
│                      │ 文件数量和变更范围自动判断                    │
├──────────────────────┼────────────────────────────────────────────┤
│ senior + junior 并行  │ 1. 不同模块独立性高，可以并行不冲突           │
│ 而非串行              │ 2. senior 做完核心后可以 Review junior       │
│                      │ 3. 模拟真实团队的工作模式                    │
├──────────────────────┼────────────────────────────────────────────┤
│ API 契约实现后冻结     │ 无数项目死在「边写边改 API」上。冻结后         │
│                      │ junior-dev 不会因为 API 变更而白干活          │
├──────────────────────┼────────────────────────────────────────────┤
│ 最多重试 3 次         │ > 3 次说明问题超出了 AI 的能力范围。          │
│ 然后上报              │ 盲目重试只会浪费 token 和时间                │
├──────────────────────┼────────────────────────────────────────────┤
│ 从文件探测技术栈       │ 不需要问用户"你用什么框架"，减少摩擦。        │
│ 而非问用户            │ 配置文件是唯一可靠的真相来源                  │
├──────────────────────┼────────────────────────────────────────────┤
│ STATE.json 作为       │ 会话随时可能断开。状态在文件里，新会话可以      │
│ 唯一真相来源          │ 读取文件恢复进度，不依赖内存                  │
├──────────────────────┼────────────────────────────────────────────┤
│ 心跳 CronJob          │ 检测死掉的轮次，防止孤儿 Round。也可以        │
│                      │ 在新会话中检测到上一个会话未完成的工作          │
├──────────────────────┼────────────────────────────────────────────┤
│ core 目录锁定给       │ junior-dev（模拟）容易犯错，而 core 代码      │
│ architect + senior   │ 的错误影响面最大。隔离权限降低风险             │
├──────────────────────┼────────────────────────────────────────────┤
│ 绝不自动 git push     │ push 是不可逆的（对别人的工作有影响）。        │
│                      │ 用户拥有部署决策权                            │
├──────────────────────┼────────────────────────────────────────────┤
│ 角色有人格             │ 人格让 AI 更容易进入角色。"Torvalds 风格"     │
│                      │ 的架构师会更严格地审查设计；"挑剔的 QA"         │
│                      │ 会测试更多边界情况                            │
└──────────────────────┴────────────────────────────────────────────┘
```

### 15.2 踩过的坑

```
┌──────────────────────────────────────────────────────────────┐
│                    开发过程中踩过的坑                          │
│                                                              │
│  坑 1：Agent 之间互相覆盖文件                                 │
│  ─────────────────────────                                   │
│  症状：两个 Agent 同时编辑 types.ts，后写入的覆盖先写入的       │
│  解决：dispatcher 保证文件列表不重叠，加了白名单/黑名单机制     │
│                                                              │
│  坑 2：心跳 CronJob 没有清理                                  │
│  ────────────────────────                                    │
│  症状：会话结束后 CronJob 还在跑，新会话又创建了新的            │
│  解决：Stage 8 必须 CronDelete；新会话启动时检查遗留 Job       │
│                                                              │
│  坑 3：AI 自动 push 了代码                                    │
│  ──────────────────────                                      │
│  症状：AI 觉得代码完成了就直接 push，用户还没审查              │
│  解决：硬性规则——绝不自动 push，等用户主动指示                  │
│                                                              │
│  坑 4：小任务走完整流程太慢                                    │
│  ──────────────────────                                      │
│  症状：改一个按钮颜色要走 8 个 Stage                           │
│  解决：加入 S/M/L/XL 自动分级，S 级只走 3 个 Stage            │
│                                                              │
│  坑 5：junior-dev 越权改 core 代码                            │
│  ─────────────────────────                                   │
│  症状：junior-dev 为了方便直接改了 core 的中间件               │
│  解决：权限矩阵 + prompt 中硬性约束 + Code Review 检查        │
│                                                              │
│  坑 6：API 契约在实现阶段被改了                                │
│  ──────────────────────────                                  │
│  症状：architect 在 Stage 3 中途改了 API 参数，代码全乱了      │
│  解决：Section 4 冻结机制——Stage 3 开始后不允许修改 API 契约    │
│                                                              │
│  坑 7：上下文窗口不够用                                       │
│  ────────────────────                                        │
│  症状：所有文档都塞进 prompt，context 溢出                     │
│  解决：每个 Agent 只读自己需要的文件，dispatcher 给最小上下文   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```
