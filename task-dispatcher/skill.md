# Task Dispatcher — 通用任务编排

> **核心原则：默认并行，只在依赖强制时串行。**

---

## 触发条件

每条用户消息到达时，先做**分解评估**，再动手：

1. 消息里有多少**独立子任务**？（1 个 → 直接做；2+ → 评估并行）
2. 任意两个子任务之间：B 是否依赖 A 的输出？不依赖 → 并行。依赖 → A 先，B 后
3. 每个子任务：是否明确到可以派发 sub-agent，还是需要主 agent 判断？

---

## 派发规则

| 子任务类型 | Agent 类型 | 何时派发 |
|-----------|-----------|---------|
| 文件搜索 / 代码探索 | `Explore` agent | 始终派发 |
| 调研 / web search / 文档抓取 | `general-purpose` agent | 始终派发 |
| 小型代码变更（1-3 文件，spec 明确） | `general-purpose` agent + 详细 prompt | spec 无歧义时派发 |
| 复杂代码 / 架构决策 | 主 agent（自己） | 不派发 — 需要判断力 |
| 面向用户的回答 / 建议 | 主 agent（自己） | 不派发 — 需要用户上下文 |

### 规模直觉

| 子任务预估耗时 | 策略 |
|--------------|------|
| < 10 秒 | 不值得派发，直接做 |
| 10 秒 ~ 2 分钟 | 派发到 background agent |
| > 2 分钟 | 派发 + 同时启动其他工作 |

---

## 派发协议

派发 sub-agent 时，主 agent **必须**做到：

### 1. 完整 briefing
Sub-agent **没有**本次对话的任何上下文。必须包含：
- **做什么**：明确目标，不含歧义
- **看哪些文件**：给出绝对路径或 glob pattern
- **返回格式**：「300 字以内报告」或「改完代码后跑 `npx tsc --noEmit` 验证」
- **不碰什么**：明确边界

### 2. 不重叠边界
> "Agent A 处理 `src/extensions/` 下的文件，Agent B 处理 `tests/`" — **绝不让两个 agent 编辑同一个文件**。

如果两个子任务需要改同一个文件 → 必须串行（一个 agent 做完再派另一个，或主 agent 自己做）。

### 3. 输出预期
每个 agent 必须知道返回什么：
- 调研型：「列出 3 个方案 + 推荐 + 理由」
- 代码型：「改完文件 + 验证命令输出」
- 探索型：「文件清单 + 关键代码片段」

### 4. Background 执行
所有派发的 agent 使用 `run_in_background: true`，主 agent 继续工作或响应用户。

---

## Agent 间协调

| 原则 | 说明 |
|------|------|
| **无共享状态** | Agent 之间看不到彼此的工作，主 agent 是唯一协调者 |
| **文件冲突** | 两个子任务改同一文件 → 必须串行 |
| **结果合成** | Agent 完成后，主 agent 读取结果并合成统一回复 — 不是简单拼接，要加判断 |

## 进度汇报

### 派发后立即
告诉用户启动了什么：

```
| # | Agent | 任务 | 状态 |
|---|-------|------|------|
| 1 | Explore | 搜索 auth 相关配置文件 | 🔄 进行中 |
| 2 | Research | 查询 Cloudflare 免费额度 | 🔄 进行中 |
| 3 | 主 Agent | 修复登录 bug | 🔄 进行中 |
```

### 单个 Agent 完成时
简短更新：「Agent 1 完成：找到 3 个配置文件。等待 Agent 2。」

### 全部完成时
合成报告 + 可执行的下一步建议。

## 什么时候不并行

直接做，别派发：

- 用户问了一个**简单问题** → 直接回答
- **单一原子任务** → 直接做
- 任务**紧密耦合**（每步需要上一步输出） → 串行
- 子任务预估 **< 10 秒** → agent 开销不值得

---

## 串行化红旗

你脑中出现以下想法时，停下来重新评估：

| 想法 | 实际情况 |
|------|---------|
| "先做 X，再做 Y" | X 和 Y 独立？那**现在就同时派发** |
| "我逐个更新这 3 个文件" | 文件间无依赖？派 3 个 agent |
| "先调研再回答" | 派调研 agent + 同时构思回答框架 |
| "先看代码再决定方案" | 派 Explore agent 看代码，同时思考方案 |
| "等这个完成再做下一个" | 下一个真的依赖这个的输出吗？ |

## 分解示例

### 示例 1：混合工作负载

用户说：「修复这个 bug，然后告诉我 Cloudflare 的免费额度是多少，然后把 R2 的配置步骤写到 DEPLOYMENT.md 里」

**分解：**
1. 修复 bug → 代码任务 → 主 agent（需要判断力）
2. Cloudflare 免费额度 → 调研 → 派发 Research agent
3. 写 R2 配置到 DEPLOYMENT.md → 文档任务 → 依赖任务 2 的结果

**依赖分析：**
- 任务 1 和 任务 2 **独立** → 并行
- 任务 3 **部分依赖**任务 2（需要调研结果）→ 任务 2 完成后派发

**执行：**
- 立即派发任务 2（background）
- 立即开始任务 1（主 agent）
- 任务 2 返回后，派发任务 3
- 全部完成 → 合成报告

### 示例 2：多文件代码变更

用户说：「在 header 加个搜索框，在 footer 加版权年份，在 sidebar 加折叠按钮」

**分解：**
1. Header 搜索框 → `src/components/Header.tsx`
2. Footer 版权年份 → `src/components/Footer.tsx`
3. Sidebar 折叠 → `src/components/Sidebar.tsx`

三个文件完全独立 → 派发 3 个 agent 并行。

### 示例 3：不可并行

用户说：「先分析一下现有的数据库 schema，然后基于分析结果设计新的 migration」

任务 2 完全依赖任务 1 的输出 → **串行**。但可以派 Explore agent 做任务 1，主 agent 拿到结果后做任务 2。

## 与 harness-workflow 的关系

| 层级 | 职责 | 谁负责 |
|------|------|--------|
| **外层分解**：用户消息有几件事要做？ | task-dispatcher |
| **内层开发**：这件代码任务怎么走 8-Stage？ | harness-workflow |

两者不冲突：
- task-dispatcher 负责「做什么」— 把消息拆成独立子任务
- harness-workflow 负责「怎么做」— 每个代码子任务走 Stage 0→8

**典型组合：** 用户消息包含 1 个代码任务 + 1 个调研任务 → task-dispatcher 派调研 agent（background），同时主 agent 用 harness-workflow 做代码任务。

## 决策流程图

```
用户消息到达
    │
    ▼
分解为子任务列表
    │
    ▼
子任务数量 = 1？ ──yes──→ 直接执行（无需编排）
    │ no
    ▼
分析依赖关系
    │
    ├─ 全部独立 → 全部并行派发
    ├─ 部分依赖 → 独立的并行，依赖的串行
    └─ 全部串行 → 按序执行（仍可派 agent 做各步）
    │
    ▼
等待结果 + 合成回复
```

## 质量保障

- **派发前**：确认 agent prompt 包含足够上下文（零上下文原则）
- **返回后**：验证 agent 产出是否符合预期，不盲信
- **冲突检测**：如果多个 agent 改了相关代码，主 agent 做最终整合审查
- **失败处理**：agent 失败 → 主 agent 接手该子任务，不重试超过 1 次
